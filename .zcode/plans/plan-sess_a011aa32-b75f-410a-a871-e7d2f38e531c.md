## الإجابة على السؤال أولاً

**لا يمكن إجبار** نافذة الـ captive portal التي يفتحها أندرويد تلقائياً على أن تكون كروم — القرار قرار النظام. لكن يوجد مسارَان حقيقيان للوصول لنفس النتيجة:

1. **المسار المعياري (RFC 8910/8908) — يفتح النظامُ المتصفحَ بنفسه**: عند ضبط DHCP option 114 على الراوتر ليشير إلى `api.json`، تستعلم أندرويد 13+ عن الـ API وتحصل على `user-portal-url` — وهو مصمَّم معيارياً ليُفتح في **متصفح المستخدم الكامل** بدلاً من WebView النظام. ملف `api.json` عندنا **جاهز أصلاً** (يحتوي `captive` + `user-portal-url: $(link-login-only)` — استجابة RFC 8908 مطابقة، تُستبدل متغيراتها لكل طلب). الناقص فقط 3 أوامر RouterOS. ملاحظات صادقة: يتطلب أندرويد 13+ على جهاز العميل (سلوك النسخ الأقدم غير مضمون)، وسلوك أندرويد الفعلي مع `user-portal-url` (فتح تلقائي في المتصفح أم زر) يحتاج تحققاً على الجهاز، واحتمال أن يقبل أندرويد API على http (وليس https) سيُحسم بالاختبار.

2. **زر «افتح في المتصفح الكامل» (intent://) — مبني بالفعل** في a794e5c ولم يُختبر على الجهاز بعد. نقرة واحدة تُخرج المستخدم من WebView إلى متصفحه الافتراضي — إن سمح WebView تطبيق النظام بذلك (سيُحسم بالاختبار).

iOS: لا شيء من هذا ينطبق (CNA لا يمكن تهريبه؛ الحل هناك هو كاميرا الهاتف مع كروت الروابط).

## خطوات التنفيذ

### 1. رفع ملفين + إعادة توصيل USB (المستخدم)
- رفع `dist/login.html` + `dist/ar/login.html` إلى مجلد البوابة على الراوتر (بناء `a794e5c` الحالي يحتوي زر الهروب والـ guide)
- إعادة توصيل الهاتف بالـ USB وإبقاء نافذة الشبكة مفتوحة

### 2. اختبار adb — الجزء الأول: إصدار أندرويد + زر الهروب
- `adb shell getprop ro.build.version.release` و `ro.build.version.sdk` → تحديد هل الهاتف يدعم RFC 8908 (13+)
- من نافذة الشبكة: الضغط على زر الماسح → التأكد من ظهور الـ guide (زر التصوير مخفي + رسالة + زر «افتح في المتصفح الكامل»)
- الضغط على «افتح في المتصفح الكامل» → `adb shell dumpsys window | grep mCurrentFocus` → هل فتح المتصفح؟ (نجاح = ظهور com.android.chrome أو المتصفح الافتراضي)

### 3. أوامر RouterOS — option 114 (المستخدم ينفذها، من runbook §5 بصيغة الـ skill المضمونة)
```routeros
/ip dhcp-server option add name=captive-portal code=114 force=yes value="'http://192.168.8.1/api.json'"
/ip dhcp-server option sets add name=captive-portal-set options=captive-portal
/ip dhcp-server set [find] dhcp-option-set=captive-portal-set
```
تنبيهات: صيغة الاقتباس المزدوج-داخل-المفرد إلزامية، و`force=yes` إلزامي (وإلا تتجاهله iOS/أندرويد)، و`[find]` يطابق كل خوادم DHCP على الراوتر إن وُجد أكثر من واحد. بعدها إعادة تشغيل الواي فاي على الهاتف (لتجديد الlease واستقبال option 114).

### 4. اختبار adb — الجزء الثاني: مسار RFC 8908
- مراقبة عند اتصال الواي فاي: `adb logcat | grep -iE "networkstack|captiveportal|8910|8908"` → هل استعلم أندرويد عن الـ API؟
- `dumpsys window` لحظة «Sign in to network» → **أي تطبيق فتح؟** CaptivePortalLogin (كالسابق) أم المتصفح (نجاح المسار المعياري)
- فحص استجابة الـ API من الهاتف نفسه: هل Content-Type الذي يخدمه RouterOS لـ .json يقبه أندرويد؟ (مخاطرة معروفة — إن رفضها أندرويد فالمسار المعياري يتوقف حتى يُحل HTTPS، ويُوثَّق ذلك)

### 5. المتابعة حسب النتيجة (تعديلات كود محتملة، كلها صغيرة)
- **إن نجح زر الهروب**: يبقى كما هو، وتُحدَّث فقرة README «Voucher QR Scanning» + runbook §5 (ترقية option 114 من «اختياري» إلى «موصى به — يوجّه أندرويد 13+ للمتصفح الكامل») مع ذكر قيد الإصدار
- **إن ابتلع WebView النظام زر الهروب**: إخفاؤه من `_showWebViewGuide()` في `src/js/modules/qr-scanner.js` (سطر واحد — يبقى النص الإرشادي وكاميرا الهاتف)
- **إن نجح مسار RFC 8908**: توثيقه في runbook كالإجابة الرسمية عن سؤال «إجبار المتصفح» مع قيد أندرويد 13+؛ وإن فشل بسبب Content-Type أو http — توثيق السبب بدقة
- تحديث CHANGELOG + ذاكرة المشروع بالنتائج الفعلية

## التحقق
- النتيجة النهائية تُقاس على جهاز حقيقي عبر adb فقط (dumpsys/logcat)، لا بالمعاينة المحلية — لأن السؤال كله عن سلوك النظام
- بعد أي تعديل كود طارئ: `npm test` + `npm run build` + `npm run test:e2e` (181 + 28 اختبار حالياً) قبل أي التزام
- لا التزامات جديدة إلا بعد انتهاء جولة الاختبار وتوثيق النتيجة
